## Решение для первого этапа

Выбрать **Keystatic в GitHub mode**.

Keystatic добавит в существующее Next.js-приложение маршрут админки `/keystatic` с формой для создания и редактирования кейсов. Данные будут храниться в GitHub-репозитории в виде файлов, поэтому на первом этапе не требуются:

- отдельный бэкенд или сервис на Go;
- база данных;
- отдельная панель хостинга для CMS.

Редактор входит через GitHub. Доступ к админке получают только пользователи с правами записи в репозиторий `maxeliseyev/studio49`. Keystatic создаёт или обновляет файлы в Git и умеет работать с ветками. После изменения контента Vercel собирает и публикует сайт как обычно.

Важно: это не полностью «без серверного кода». Для GitHub OAuth Keystatic использует API routes внутри Next.js и переменные окружения. Однако отдельной инфраструктуры и постоянно работающего сервиса не понадобится.

Источники:

- [Keystatic: introduction](https://keystatic.com/docs/introduction)
- [Keystatic: GitHub mode](https://keystatic.com/docs/github-mode)

## Данные кейса

В форме администратора предусмотреть следующие поля:

| Поле | Тип | Обязательное |
| --- | --- | --- |
| Название | строка | да |
| Slug | строка, уникальная | да |
| Категории | множественный выбор: логотип, брендинг, веб-дизайн, разработка | да |
| Год | число | да |
| Ссылка «кейс» | URL | нет |
| Ссылка «сайт» | URL | нет |
| Обложка | изображение | нет |
| Описание | текст / rich text | нет |
| Порядок показа | число | нет |
| Статус | черновик / опубликован | да |

На сайте список проектов будет строиться из этих записей, а текущий селектор категорий — фильтровать их по полю `categories`.

## План внедрения, когда CMS понадобится

1. Вынести текущий массив кейсов из `app/page.tsx` в контентные файлы.
2. Подключить Keystatic и описать схему кейса.
3. Добавить маршрут `/keystatic` и локальный режим редактирования для разработки.
4. Настроить GitHub mode: GitHub App, OAuth redirect URL и переменные окружения на Vercel.
5. Перенести существующие кейсы и ссылки в новую структуру.
6. Перевести страницу проектов на чтение контентных файлов.
7. Проверить сценарий редактора: создать черновик, добавить обложку, открыть preview, опубликовать.

Изображения небольшого размера можно на старте коммитить в репозиторий. Если число или вес обложек заметно вырастет, вынести медиа в отдельное объектное хранилище/CDN.

## Почему не другие варианты сейчас

### Decap CMS

Тоже хранит контент в Git, но production-авторизация требует GitHub OAuth-посредника или Netlify Identity / Git Gateway. Для этого проекта Keystatic даёт более прямой путь через GitHub и Next.js.

Источник: [Decap CMS backends](https://decapcms.org/docs/backends-overview/).

### Sanity

Стоит рассмотреть при нескольких редакторах, совместной работе, развитой медиатеке, черновиках и визуальном preview. Sanity не требует собственного сервиса, но использует внешний hosted content backend.

Источник: [Sanity + Next.js](https://www.sanity.io/docs/nextjs/introduction).

### Payload

Не выбирать на первом этапе: Payload требует базу данных и настройку постоянного хранения загружаемых файлов. Он уместен, если понадобится полностью собственная CMS с API и сложными ролями.

Источник: [Payload installation](https://payloadcms.com/docs/getting-started/installation).

## Условия пересмотра решения

Перейти на Sanity или Payload, если появится хотя бы одно из условий:

- несколько редакторов с разными ролями и процессом согласования;
- частые изменения контента без желания хранить их как Git-коммиты;
- большая медиатека или тяжёлые изображения;
- необходимы сложные черновики, предпросмотр и история публикаций;
- данные кейсов начинают использоваться сторонними приложениями через API.
